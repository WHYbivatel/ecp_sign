# Аппаратные токены: первый носитель и интеграция

Этап 5 [плана](extension-improvement-plan.md). Состояние на 12.11.2026: **готов только интеграционный код
прототипа**. Физическое устройство не испытано. Поддержка токенов в расширении не включена: клиент не подключён
к окнам, в манифесте нет разрешения `nativeMessaging`, файловые ключи работают как раньше.

## Что есть у NCALayer

Официальный Kalkan 0.7.8 из `ncalayer.zip` работает с токенами через PC/SC (`javax.smartcardio`) своим закрытым
кодом APDU, без PKCS#11 производителя. Классы в `kz/gov/pki/kalkan/pcsc/`:

| Носитель | Класс Kalkan | Хранилище |
|---|---|---|
| KAZTOKEN | `Kaztoken` | `AKKaztokenStore` |
| Удостоверение личности РК | `KZIDCard` | `AKKZIDCardStore` |
| SafeNet eToken 72K | `EToken72K` | `AKEToken72KStore` |
| SafeNet eToken 5110 | `EToken5110` | `AKEToken5110Store` |
| JaCarta | `JaCarta` | `AKJaCartaStore` |
| A-Key | `AKey` | `AKAKEYStore` |

Ключи: `AKRSAPrivateKey`, `AKGOST34310PrivateKey`, `AKGOST3410_2015PrivateKey`. Протокол APDU не опубликован.

## Способы интеграции

| Способ | Что даёт | Препятствие | Решение |
|---|---|---|---|
| Native Messaging + PKCS#11 производителя | документированный интерфейс (OASIS PKCS#11), ключ не покидает токен, PIN-пад через `CKF_PROTECTED_AUTHENTICATION_PATH` | нужна программа на компьютере и драйвер производителя; механизмы ГОСТ РК есть не у всех модулей | **выбран для первого носителя** |
| Native Messaging + Kalkan по PC/SC | те же носители, что у NCALayer, включая ГОСТ и KAZTOKEN | лицензия на распространение Kalkan не известна; нужна Java; нужно согласие НУЦ | отложен до ответа НУЦ |
| WebUSB / WebHID | без установки программ | протокол APDU носителей закрыт; Chromium не даёт доступ к классу смарт-карт (CCID); Firefox WebUSB не поддерживает | отклонён |

Native Messaging меняет свойство «без дополнительных программ»: для токенов нужен отдельный установщик.
Файловые ключи от него не зависят.

## Первый носитель и ОС

- **Устройство для испытаний:** SafeNet eToken 5110 (есть в списке Kalkan; документированный PKCS#11 в SafeNet
  Authentication Client). Альтернатива — JaCarta с документированным PKCS#11 производителя.
- **ОС:** Windows 11 x64 (основная ОС пользователей НУЦ) или Ubuntu 22.04 x64; первой берётся та, для которой есть
  устройство и драйвер.
- **Ключ:** синтетический RSA 2048 и самоподписанный сертификат, записанные на токен для испытаний. Реальный ключ
  НУЦ на токене проверяет владелец.
- **Имя библиотеки PKCS#11** (например, `eTPKCS11.dll` / `libeTPKCS11.so`) сверить с документацией SafeNet перед
  установкой; в реестр модулей вносится только путь из этой документации.
- ГОСТ РК на токене (KAZTOKEN) требует документации производителя по механизмам PKCS#11 либо пути через Kalkan.
  Обещаний по ГОСТ на токене нет.

На сервере разработки физического токена нет (`lsusb`: только корневые хабы). Испытания на устройстве не
проводились.

## Минимальный сценарий

1. Обнаружить токен: `list` возвращает токены с сертификатами.
2. Выбрать сертификат в окне Tegin.
3. Подписать тестовый документ: CMS/CAdES-BES attached, RSA SHA-256. Подпись проверяют Tegin `verifyCms` и
   `openssl cms -verify`; на устройстве — также официальный Kalkan.
4. Отмена до ввода PIN и во время операции.
5. Извлечение устройства между выбором и подписью.

## Архитектура

```
страница ──(протокол NCALayer)── расширение: окно подтверждения Tegin
                                          │ runtime.connectNative('kz.tegin.token')
                                          ▼
                               локальный компонент kz.tegin.token
                                          │ PKCS#11 (модуль из реестра установщика)
                                          ▼
                                     токен: ключ, C_Sign
```

- Страница не общается с компонентом: порт Native Messaging открывает только страница расширения.
- Компонент подписывает переданные байты (`CKM_SHA256_RSA_PKCS`) — для CMS это `SignedAttributes`. Закрытый ключ
  не покидает токен.
- Библиотеки PKCS#11 берутся только из реестра, который пишет установщик (в прототипе `TEGIN_TOKEN_MODULES`).
  Сообщение не может назвать библиотеку: лишние поля дают `BAD_REQUEST`.
- Перед подписью компонент заново сверяет серийный номер токена и SHA-256 сертификата. Если токен извлечён,
  заменён или сертификат другой — `TOKEN_REMOVED` / `KEY_NOT_FOUND`, подписи нет.

## PIN

- PIN вводится в окне подтверждения Tegin (страница расширения, сайту недоступна) или на PIN-паде устройства.
  Для PIN-пада компонент вызывает `C_Login` без PIN, и клиент PIN не передаёт.
- PIN есть только в сообщении `sign`, уходит в `C_Login` и сбрасывается. Он не попадает в ответы, журнал
  компонента (JSON только с полями `event`, `op`, `code`, `ckr`, `found`, `module`) и сообщения об ошибках.
- Неверный PIN не повторяется автоматически: `PIN_INCORRECT` возвращается окну. Флаги `pinCountLow`,
  `pinFinalTry`, `pinLocked` показываются до ввода; заблокированный PIN — `PIN_LOCKED` без попытки входа.
- Ограничение прототипа: в Python строку PIN нельзя обнулить в памяти. Продуктовый компонент — подписанная
  скомпилированная программа, обнуляющая буфер PIN.

## Протокол v1

Кадр — 32-битная длина в порядке байтов платформы и JSON в UTF-8 (формат Native Messaging), сообщение до 64 КБ,
данные для подписи до 16 КБ. Каждое сообщение: `v: 1`, `id` (строка до 64 символов), `op`.

| `op` | Поля запроса | Ответ |
|---|---|---|
| `hello` | — | `host`, `protocol`, имена модулей, `mechanisms` |
| `list` | — | `tokens[]`: `module`, `slot`, `label`, `manufacturer`, `model`, `serial`, флаги PIN, `certificates[]` (`keyId`, `label`, `certificate`, `sha256`) |
| `sign` | `module`, `slot`, `serial`, `keyId`, `certificateSha256`, `mechanism: "RSA-PKCS-SHA256"`, `data`, `pin` (нет для PIN-пада) | `signature` |
| `cancel` | `target` | `cancelled` |

Ошибка: `ok: false, code`. Коды: `PIN_INCORRECT`, `PIN_LOCKED`, `PIN_LEN_RANGE`, `PIN_INVALID`, `PIN_REQUIRED`,
`TOKEN_REMOVED`, `KEY_NOT_FOUND`, `MECHANISM_UNSUPPORTED`, `CANCELLED`, `BUSY`, `BAD_REQUEST`, `DEVICE_ERROR`,
`TOKEN_ERROR`; на стороне клиента `HOST_UNAVAILABLE`, `TIMEOUT`, `BAD_RESPONSE`. Окну показываются постоянные
русские тексты (`TOKEN_MESSAGES`), текст ошибки токена не пробрасывается.

Отмена: клиент сразу завершает ожидание с `CANCELLED` и отправляет `cancel`; компонент проверяет отмену перед
входом и перед подписью. Если `C_Sign` уже начался, подпись токена отбрасывается клиентом.

## Установка, обновление, доверие (для продуктового компонента)

- Отдельный установщик: подписанный исполняемый файл (Authenticode на Windows), манифест Native Messaging для
  Chrome/Edge (`allowed_origins` — только ID расширения Tegin) и Firefox (`allowed_extensions`), реестр путей
  PKCS#11.
- Обновления — новой подписанной версией установщика; компонент не загружает код и не ходит в сеть.
- Расширение проверяет `hello.protocol` и отказывает при неизвестной версии.
- Без компонента окно предлагает файловый ключ; файловые ключи работают без установщика.

## Что проверено (SoftHSM2 вместо устройства)

`tests/token-softhsm.mjs` (локально в одноразовом Docker-контейнере `tests/token-softhsm.sh`, в CI — задача
`token-host`): SoftHSM2 2.6, токен с синтетическим RSA-ключом и сертификатом, компонент — `native-host/tegin_token_host.py`
через тот же кадр Native Messaging.

- `hello` и `list`; CMS через `tokenSigner` → проверяют Tegin `verifyCms` и `openssl cms -verify`.
- Неверный PIN: одна попытка, `PIN_INCORRECT`, повтора нет.
- Сообщение с полем `library` → `BAD_REQUEST`.
- Отмена во время операции (тестовая пауза перед входом) → `CANCELLED`, подписи нет.
- Удаление токена → `TOKEN_REMOVED`, список пуст. Другой токен на месте прежнего → прежний выбор `TOKEN_REMOVED`,
  чужой SHA-256 сертификата → `KEY_NOT_FOUND`.
- Журнал компонента без PIN и только с разрешёнными полями.

`tests/token-client.test.js` (7 тестов): проверка ответа `list`, PIN только в `sign`, PIN-пад без PIN, неверный
PIN не повторяется и не попадает в ошибку, отмена, обрыв порта, коды ошибок, ГОСТ отклоняется до запроса.

## Не проверено

Физическое устройство и драйвер; извлечение во время `C_Sign`; горячее подключение (SoftHSM не показывает новые
токены работающему процессу, поэтому замена проверена новым экземпляром компонента); PIN-пад; ГОСТ на токене;
Windows и macOS; манифесты Native Messaging в браузерах; одновременная работа с NCALayer и другими программами,
держащими токен; смена PIN токена.

## Комплект для испытания на устройстве

Устройства пока нет. Всё ниже готово к запуску, как только оно появится.

**Оборудование и ОС.** Один SafeNet eToken 5110 (или JaCarta), на котором нет нужных ключей: при испытании
на него записывается синтетический ключ. Компьютер с Windows 11 x64 или Ubuntu 22.04 x64, Node 22, Python 3 с
`PyKCS11`, OpenSSL. Для сверки с Kalkan — Java 17 и `scripts/fetch-kalkan.mjs`.

**Драйвер.** SafeNet Authentication Client (для JaCarta — «Единый клиент JaCarta») с сайта производителя, версия
на дату испытания, записывается в отчёт. Путь к библиотеке PKCS#11 берётся из документации этой версии; на
Windows он обычно в `System32`, на Linux в `/usr/lib`. Других путей не пробовать.

**Подготовка ключа.** Синтетический RSA 2048 и самоподписанный сертификат:

```bash
openssl req -x509 -newkey rsa:2048 -nodes -keyout trial.key -out trial.pem -days 30 -subj "/CN=Tegin token trial"
openssl pkcs12 -export -inkey trial.key -in trial.pem -out trial.p12
```

`trial.p12` импортируется на токен средствами клиента производителя (SAC Tools → «Импорт сертификата»). После
этого `trial.key` удаляется. PIN токена — тестовый, не от рабочего носителя.

**Запуск.** Из корня репозитория, после `npm ci`:

```bash
TEGIN_TOKEN_MODULES=<путь из документации> TEGIN_TOKEN_PIN=<тестовый PIN> TEGIN_TOKEN_OUT=token-trial \
  node tests/token-device.mjs
```

Скрипт `tests/token-device.mjs` запускает компонент `native-host/tegin_token_host.py` через тот же кадр
Native Messaging, что и расширение, и проходит минимальный сценарий:

1. `hello` и `list` находят токен и сертификат.
2. CAdES-BES тестового документа подписывается на токене и проверяется Tegin `verifyCms` и `openssl cms -verify`.
3. С `TEGIN_TOKEN_WRONG_PIN=1` — один неверный PIN: `PIN_INCORRECT`, повтора нет, видны флаги счётчика.
   Это тратит одну попытку.
4. Отмена сразу после запроса: `CANCELLED`, подписи нет.
5. По подсказке токен извлекается: прежний выбор даёт `TOKEN_REMOVED`, список пуст.
6. По подсказке токен вставляется обратно: подпись через новое подключение компонента проходит.
7. В журнале и ответах компонента нет PIN.

В конце печатается JSON-отчёт: ОС, имя модуля, модель токена, флаги PIN, коды и время шагов. Серийных номеров,
сертификата и PIN в нём нет. Этот отчёт и версию клиента производителя нужно вернуть. Файлы `token-trial/document.p7s`,
`document.txt` и `signer.der` остаются у испытателя для проверки Kalkan.

Скрипт проверен на SoftHSM2 в одноразовом контейнере: извлечение и вставка имитировались удалением и созданием
токена. Все шаги прошли. Отмену во время `C_Sign` и PIN-пад скрипт не проверяет: для них нужен ручной шаг
(раздел ниже).

## План испытаний на устройстве

1. Установить SafeNet Authentication Client по документации, записать синтетический RSA-ключ и сертификат.
2. Внести путь PKCS#11 из документации в реестр, запустить `hello` и `list`.
3. Подписать тестовый документ: проверка Tegin, OpenSSL и официальным Kalkan.
4. Неверный PIN один раз; убедиться, что счётчик попыток уменьшился на одну и `pinCountLow` виден.
5. Отмена до ввода PIN и во время операции.
6. Извлечь токен после выбора сертификата → `TOKEN_REMOVED`; извлечь во время подписи → ошибка без подписи.
7. Журналы компонента и браузера: PIN и данные документа отсутствуют.
