# Проверка отзыва сертификатов (OCSP/CRL)

Этап 2 плана [extension-improvement-plan.md](extension-improvement-plan.md). Ветка
`codex/certificate-revocation` от `8f01566` (`codex/portal-compatibility`). Исследование
и измерения выполнены 09.11.2026. Своего сервера, прокси и Native Host нет.

## Первичные источники

- Страница разработчиков НУЦ: <https://pki.gov.kz/ru/developers/>. Разделы «Сервис OCSP»
  (`http://ocsp.pki.gov.kz/`), «Список отозванных сертификатов» (боевые и резервные адреса
  `crl.pki.gov.kz` / `crl1.pki.gov.kz`, полный и delta CRL для RSA и ГОСТ), «Служба меток
  времени» (`http://tsp.pki.gov.kz`).
- Сертификаты УЦ: <https://pki.gov.kz/ru/cert/>. Точки распространения CRL корневых УЦ взяты
  из расширения CRL Distribution Points сертификатов `nca_rsa_2022` и `nca_gost_2022`:
  `http://crl.root.gov.kz/rsa2020.crl` и `http://crl.root.gov.kz/gost2015_2022.crl`.
  Те же файлы отдаются по HTTPS, расширение использует HTTPS.
- Правила проверки подлинности ЭЦП (приказ № 500/НҚ): <https://adilet.zan.kz/rus/docs/V2600039672>.
  - п. 4 пп. 3: сначала OCSP, CRL — если OCSP недоступен; delta CRL уточняет CRL;
  - п. 14: при наличии действительной метки времени проверка выполняется на момент метки;
  - п. 17: требования к метке времени и сертификату TSA;
  - п. 18: проверки CRL — структура, издатель, связь, подпись, период действия;
  - п. 19: проверки OCSP — структура, ответчик от того же УЦ, CertID, подпись, OCSPSigning,
    thisUpdate не раньше момента проверки, допустим только `good`.
- Правила выпуска и отзыва регистрационных свидетельств, ссылка со страницы разработчиков:
  <https://adilet.zan.kz/rus/docs/V2600039747#z444>.
- Регламент (CPS) НУЦ РК v3: <https://pki.gov.kz/docs/npa/CERTIFICATION%20PRACTICE_STATEMENT_v3.pdf>.
  §2.3: СОРС публикуется раз в сутки; дельта СОРС содержит свидетельства, «отозванные с момента
  выпуска последнего основного СОРС». На этом основан профиль совместимости НУЦ (см. «Delta CRL»).
- RFC 6960 (OCSP), RFC 5280 (CRL, delta CRL; совместимость полного и delta —
  [§5.2.4](https://www.rfc-editor.org/rfc/rfc5280.html#section-5.2.4)), RFC 3161 (метки времени).

Адреса взяты только со страницы НУЦ и из опубликованных сертификатов УЦ. Расширение никогда
не обращается к адресам из AIA, CRL DP или Freshest CRL проверяемого сертификата.

## Измерения служб (09.11.2026)

| Служба | Факты |
|---|---|
| `http://ocsp.pki.gov.kz/` | Только HTTP: по HTTPS ответ 405. Нет CORS: preflight `OPTIONS` → 405. Принимает POST и GET, CertID с SHA-1 и SHA-256. Ответ `application/ocsp-response`, 1,3–2 КБ. Nonce возвращается точно. `nextUpdate` нет, `thisUpdate` = `producedAt` ≈ текущее время. Ставит cookie без имени: расширение шлёт `credentials: 'omit'` |
| Ответчики OCSP | Делегированные «OCSP RSA» и «OCSP GOST» (ключ RSA-2048), выданы `nca_rsa_2022` / `nca_gost_2022`, действуют 02.07.2026–02.07.2027. EKU OCSPSigning, KU digitalSignature (критическое), `id-pkix-ocsp-nocheck`. Сертификат ответчика вложен в ответ, ResponderID по имени. В каждом ответе некритическое `id-pkix-ocsp-extended-revoke` |
| Невыданный серийный номер | Ответ `revoked`, `certificateHold`, время отзыва 01.01.1970 и `extended-revoke`: соглашение RFC 6960 §2.2 «не выдавался». Tegin трактует это как «статус неизвестен» |
| OCSP для промежуточных УЦ | `malformedRequest`, поэтому промежуточные проверяются по CRL корневых УЦ |
| Полный CRL RSA | 96 648 Б, действует ≈27 ч, номер 1468, 1834 записи |
| Delta CRL RSA | 1013 Б, ≈12 ч, номер 63642, критический Delta CRL Indicator = 1468 |
| Полный CRL ГОСТ | 20 253 730 Б, ≈27 ч, номер 1469, 390 737 записей. Проверка подписи Стрибог-512 ≈3,8–4,5 с, поиск ≈0,8 с (Node) |
| Delta CRL ГОСТ | 84 275 Б, ≈12 ч, номер 63633, Delta CRL Indicator = 1469 |
| CRL корневых УЦ | 842 Б (RSA), 471 Б (ГОСТ), без записей, действуют до 04.12.2026, `application/pkix-crl` |

Общее для CRL НУЦ:

- подпись `sha256WithRSA` (RSA) или 1.2.398.3.10.1.1.2.3.2 (ГОСТ);
- есть AKI и CRL Number; нет IDP, то есть нет секционированных и косвенных списков;
- полные и delta CRL нумеруются отдельными последовательностями (≈1,5 тыс. и ≈63 тыс.).
  RFC 5280 §5.2.3 требует одну общую последовательность, поэтому условие §5.2.4 (d)
  «номер полного < номера delta» для НУЦ выполняется всегда и не отличает старую delta от новой;
- база delta равна номеру текущего полного списка, `thisUpdate` у пары одинаковый
  (RSA 00:35:02, ГОСТ 00:45:02 UTC). Повторная проверка 09.11.2026 в 11:22 UTC показала те же
  пары: delta действует ≈12 ч, а не «каждый час, не более 2 часов», как сказано в §2.3 CPS;
- тип `application/octet-stream`; перенаправлений и CORS-заголовков нет;
- основной и резервный файлы совпадают побайтно.

### Эксперимент в браузере

Сборка расширения в Chromium (Playwright). Запросы из страницы расширения того же origin,
что и Worker, с теми же опциями `fetch`, что в коде:

| Запрос | С разрешением `http://ocsp.pki.gov.kz/*` | Без него |
|---|---|---|
| POST OCSP | 200, `application/ocsp-response`, ответ `basic`, не opaque | `TypeError: Failed to fetch` |
| CRL корневого УЦ (HTTPS) | 200, `application/pkix-crl` | 200 (покрыт `https://*.kz/*`) |
| Delta CRL НУЦ (HTTPS) | 200 | 200 |

Обход CORS обеспечивают разрешения хоста, отдельный сервер не нужен. WAF на `crl.root.gov.kz`
возвращает HTML «Веб-страница заблокирована!» (HTTP 500) для User-Agent `HeadlessChrome`.
С обычным User-Agent Chrome, в том числе с `Origin: chrome-extension://…`, ответ 200. Живой
E2E поэтому запускает браузер с обычным User-Agent. Для пользователей это не ограничение,
но доступность этой службы вне нашего контроля.

## Архитектура

```
approve.js ──postMessage──> crypto/worker.js
                                 │ open: verifyChain → revocationPath → RevocationChecker.checkPath
                                 │ sign: повторная проверка, если истёк срок доказательств (expires)
                                 │       или прошло > 5 мин; подпись; TSA-цепочка; снова срок перед выдачей
                                 │ verify: только при checkRevocation = true
                                 ▼
                        crypto/revocation.js ── fetchBounded (белый список, лимиты, отмена)
                          │            │
                    crypto/ocsp.js  crypto/crl.js  ← crypto/der.js (строгий DER)
                          │
                 crypto/revocation-profiles.js (адреса по SHA-256 сертификата издателя)
```

- `revocation-profiles.js`: источники закреплены за SHA-256 сертификата издателя. Для
  `nca_rsa_2022`/`nca_gost_2022`: OCSP, затем `crl`/`crl1` и их delta. Для корневых
  `root_rsa_2020`/`root_gost_2022`: только CRL с `crl.root.gov.kz`. Другие издатели
  получают «не проверялся».
- Путь: для цепочки сайта с якорями из `signerParams.chain` используется путь до встроенных
  корней НУЦ, если он строится. Иначе используется путь до якоря сайта, тогда издатели
  обычно не закреплены.
- Порядок для сертификата:
  1. OCSP. Проверенный ответ `good`, `revoked`, `unknown` или «не выдавался» окончателен.
  2. При сетевой ошибке или непрошедшем проверку ответе — полный CRL (основной, затем резерв).
  3. Delta CRL, если он доступен и совместим с полным (см. «Delta CRL»). Без delta принимается
     полный CRL (п. 4 Правил), источник указывается.
  4. Нет доказательства — «проверка недоступна».
- Итог по цепочке: отозван > неизвестен > проверка недоступна > не проверялся > не отозван.
  «Не отозван» показывается, только если такой результат у каждого проверяемого сертификата.
  `required` = хотя бы один издатель в пути закреплён. Тогда «не проверялся» у другого
  звена тоже блокирует.

### Проверки доказательств

OCSP (`ocsp.js`):

- `responseStatus` = successful, тип `id-pkix-ocsp-basic`, ResponseData v1, строгий DER
  без лишних байтов;
- ответчик:
  - сам УЦ — только при наличии у него OCSPSigning;
  - иначе делегированный сертификат из ответа: тот же издатель (DN и AKI/SKI), подпись УЦ
    проверена, OCSPSigning, digitalSignature, нет неизвестных критических расширений,
    действует сейчас, есть `id-pkix-ocsp-nocheck`;
- подпись ответа над точными байтами `tbsResponseData`;
- nonce обязателен (16 случайных байт в каждом запросе). Принимается как вложенная
  OCTET STRING или сырые байты;
- ровно один SingleResponse с CertID запроса (SHA-256 хеши имени и ключа издателя,
  серийный номер);
- неизвестные критические расширения ответа и SingleResponse отклоняются;
- время:
  - `thisUpdate`/`producedAt` не позднее текущего времени + 5 мин и не раньше чем 5 мин назад;
  - `nextUpdate`, если есть, не раньше текущего времени − 5 мин.

CRL (`crl.js`):

- версия 2;
- совпадение внутреннего и внешнего алгоритма;
- DN издателя = subject УЦ, AKI = SKI, у УЦ есть cRLSign;
- подпись над точными байтами `tbsCertList`;
- время: `thisUpdate` не в будущем (с допуском 5 мин), `nextUpdate` обязателен и не истёк;
- CRL Number обязателен;
- у полного списка нет Delta CRL Indicator, у delta есть;
- IDP (секционированный или косвенный CRL), запись с `certificateIssuer`, любое неизвестное
  критическое расширение списка или записи — список не используется;
- повторяющийся серийный номер — ошибка;
- `removeFromCRL` в delta снимает только приостановку (`certificateHold`).

#### Delta CRL

`deltaRelation` (`crl.js`) относит delta к полному списку: «совместима», «старше полного»,
«требует более нового полного», «противоречит». Издатель (DN и AKI) должен совпадать, область
одинакова, потому что списки с IDP отклоняются.

| Профиль | Где | Совместима | Старше полного | Требует нового полного | Противоречит |
|---|---|---|---|---|---|
| `rfc5280` (§5.2.4 a–d) | CRL корневых УЦ и любые другие | номер полного ≥ базы и < номера delta | номер delta ≤ номера полного | номер полного < базы | — |
| `nca` | только закреплённые `nca_rsa_2022` и `nca_gost_2022` | база = номеру полного и `thisUpdate` delta ≥ полного | база < номера полного и delta выпущена не позже | база > номера полного и delta выпущена не раньше | любое другое сочетание |

Профиль `nca` обоснован §2.3 CPS (delta — изменения с последнего полного списка) и
наблюдением выше. Номера двух последовательностей между собой не сравниваются.

Что получается:

- «совместима» — полный список плюс delta;
- «старше полного» — только полный список: в нём уже есть всё, что было в старой delta. Старая
  delta с `removeFromCRL` не снимает более новую приостановку;
- «требует нового полного» или «противоречит» — разрешающего ответа нет. `revoked` остаётся,
  только если полный список содержит отзыв не по `certificateHold`: такой отзыв окончателен
  (RFC 5280 §5.3.1). Иначе ошибка `CRL_DELTA_MISMATCH` и «проверка недоступна».

Если первая пара несовместима, причина может быть в кэше или в зеркале из другого цикла
публикации. Тогда все delta скачиваются заново в обход кэша, а затем полные списки по одному,
пока для самого нового полного не исчезнет более новая delta. Выбирается самый новый полный
список и самая новая совместимая с ним delta. Если любая delta требует более нового полного,
итог не разрешающий. Прежний откат «при ошибке delta взять один полный» удалён: именно он давал
`good` при delta, требующей более нового полного.

## Политика

| Операция | Цепочка НУЦ (издатели закреплены) | Цепочка без закреплённых источников |
|---|---|---|
| Вход и подписание по запросу сайта | Нужен «не отозван». Иначе ошибка до подтверждения, сайту уходит только отмена | «Не проверялся» показан явно, операция разрешена, как до этапа 2 |
| Локальное подписание файла | Так же строго, без обхода | То же |
| Подписание с меткой времени | Плюс цепочка TSA: при любом итоге, кроме «не отозван», подпись не выдаётся | Только НУЦ TSA (адрес фиксирован) |
| Проверка файла | Без сети. По отметке «Проверить отзыв онлайн» показывается текущий статус подписанта и TSA и сопоставление с меткой | Статус «не проверялся» с причиной |

Перед открытием ключа форма сообщает, что для сертификата НУЦ после открытия будет запрос
в НУЦ.

### Срок актуальности доказательств

У каждого сертификата пути есть `expires`. Для OCSP это меньшее из `nextUpdate` и
`thisUpdate` + 5 мин. Для CRL это меньшее из `nextUpdate` полного списка и использованной
delta. Итог `checkPath` хранит самый ранний срок по всей цепочке, `isCurrent` проверяет его
вместе с ограничением «не старше 5 минут от `checkedAt`». Время последнего вызова срок
доказательств не заменяет.

Worker проверяет актуальность:

1. При открытии ключа. Если срок истёк ещё до конца проверки (например, медленная загрузка
   корневого CRL), итог «проверка недоступна».
2. Перед формированием подписи. Если срок истёк, статус запрашивается заново до чтения
   первого документа.
3. После подписания пакета и проверки цепочки TSA, перед выдачей результата. Устаревшие
   доказательства подписанта и TSA обновляются, не более трёх проходов.

`revoked`, `unknown` и «проверка недоступна» блокируют операцию по утверждённой политике,
сайт получает только отмену.

Обхода при сетевой ошибке нет, ни тихого, ни явного. Владелец выбрал этот вариант (A)
из трёх: A — строго везде; B — строго для сайта, а локальное подписание с явной пометкой
«без проверки отзыва»; C — явный обход недоступности везде.

### Историческая подпись

Текущий статус не превращается в вердикт о прошлой подписи. При онлайн-проверке файла
показывается:

- «отозван позже метки времени»: метка подтверждает, что подпись существовала до отзыва;
- «отозван раньше метки времени»: на момент метки сертификат уже был отозван;
- «момент подписания не подтверждён»: метки нет.

Заголовок результата меняется на «Подпись соответствует документу» с предупреждением, без
слова «недействительна». Проверка метки на прошлый момент (п. 14 Правил) по архивным
доказательствам (CAdES-LT/LTA) не реализована: это этап 3.

## Сеть и приватность

- **Разрешения.** `host_permissions`: добавлен только `http://ocsp.pki.gov.kz/*`.
- **CSP `connect-src`.** Точные origin: `http://tsp.pki.gov.kz`, `http://ocsp.pki.gov.kz`,
  `https://crl.pki.gov.kz`, `https://crl1.pki.gov.kz`, `https://crl.root.gov.kz`.
- **Белый список.** 11 точных URL (`ALLOWED_URLS`), остальное отклоняется до запроса.
- **Опции `fetch`.** `redirect: 'error'`, `credentials: 'omit'`, `cache: 'no-store'`,
  `referrerPolicy: 'no-referrer'`. Дополнительно проверяются `response.url`, `redirected`
  и тип ответа.
- **Частные адреса.** Браузер не даёт расширению управлять DNS, поэтому гарантия ограничена
  фиксированными публичными именами хостов. Адреса сайта или сертификата не используются.
- **Лимиты.**

  | Что | Размер | Таймаут |
  |---|---|---|
  | OCSP | 64 КБ | 10 с |
  | CRL корневого УЦ | 256 КБ | 15 с |
  | Delta CRL | 4 МБ | 30 с |
  | Полный CRL | 48 МБ | 120 с |

  Размер проверяется по `Content-Length` и при потоковом чтении. Отмена объединяет внешний
  сигнал и таймаут, без `AbortSignal.any` (Chrome 111). Закрытие окна или смена ключа
  завершает Worker, а поздние сообщения отбрасываются по номеру поколения.
- **Что получает НУЦ.** OCSP: SHA-256 хеши имени и открытого ключа УЦ, серийный номер
  сертификата и случайный nonce. CRL: ничего о пользователе, скачивается публичный файл.
  Служба видит IP-адрес и время запроса. OCSP идёт по HTTP, поэтому серийный номер виден и
  посредникам в сети. Подделку исключает проверка подписи и nonce, а блокировка приводит
  к «проверка недоступна». Ключ, пароль и документ не передаются.
- **Хранение.**
  - Ответы OCSP с серийным номером пользователя хранятся только в памяти Worker текущей
    операции, не дольше 5 минут, до 32 записей.
  - Публичные CRL лежат в Cache Storage расширения (`tegin-crl-v1`) до `nextUpdate` и
    перепроверяются при каждом использовании.
  - В диагностику и журналы статусы, серийные номера и ответы не пишутся.

## Тесты

Обычные тесты используют синтетическую PKI (`tests/helpers/pki.js`) и сохранённые публичные
ответы НУЦ (`tests/fixtures/revocation/`, `provenance.json`). Реальных служб они не трогают.
Сохранены:

- ответ `good` для сертификата службы меток НУЦ;
- два ответа «не выдавался» для случайных серийных номеров;
- CRL корневых УЦ без записей.

Серийных номеров реальных отозванных сертификатов в репозитории нет.

Сценарии `tests/e2e-revocation.mjs`:

1. Не отозван: карточка сертификата и подпись.
2. Повторное использование CRL из кэша; OCSP не кэшируется между операциями.
3. Отозван: блокировка до подтверждения.
4. `unknown` без отката на CRL.
5. Обе службы недоступны: «проверка недоступна», кнопка заблокирована.
6. Откат на CRL + delta: `good` и `revoked`.
7. Промежуточный УЦ не проверен: блокировка.
8. Поздний `good` от брошенной проверки не применяется к новой (`revoked`).
9. Инструмент проверки без отметки не уходит в сеть.

Тестовая сборка включается только переменными `TEGIN_TEST_REVOCATION_ISSUERS` и `TEGIN_DIST`.
Она собирается в отдельный каталог и помечена в имени. Синтетические УЦ в ней получают те же
закреплённые адреса НУЦ, которые в тесте обслуживает локальный маршрут, а настоящие имена
хостов не резолвятся.

Результаты — в разделе «Этап 2» файла [extension-improvement-progress.md](extension-improvement-progress.md).

## Ограничения и неподтверждённое

- Firefox проверен только во временной установке, где разрешения хостов выдаются сразу. Для
  подписанной сборки из AMO выдачу при установке и последствия отзыва разрешения пользователем
  нужно проверить отдельно. Без разрешения на OCSP проверка переходит на CRL. Без разрешений
  и на OCSP, и на CRL операция блокируется, ложного `good` нет. Сам Firefox повторяет GET при обрыве соединения, поэтому при недоступном
  CRL запросов больше, чем в Chromium.
- Ответ `good` от НУЦ для сертификата реального абонента не наблюдался: личные сертификаты
  не использовались. Положительный живой результат получен для публичного сертификата службы
  меток НУЦ. Отрицательный — для случайных невыданных серийных номеров.
- `revoked` от настоящего OCSP НУЦ разобран при исследовании средствами OpenSSL. Кодом
  расширения он проверен только на синтетических ответах. Записи об отзыве в настоящих CRL
  код расширения нашёл и проверил на скачанных списках, в репозиторий они не попали.
- Резервный путь для ГОСТ-сертификатов скачивает CRL на 20 МБ. В Node проверка заняла ≈8 с.
  В слабом браузере это будет дольше, но ограничено таймаутом 120 с.
- Статус самого ответчика OCSP не проверяется: так требует `id-pkix-ocsp-nocheck`.
  Некритическое расширение ответчика 1.2.398.3.3.5 не интерпретируется.
- Используются локальные часы с допуском ±5 минут. Сильно неверные часы дают «проверка
  недоступна».
- Профиль `nca` зависит от практики НУЦ: delta строится от последнего полного списка. Если НУЦ
  перейдёт на общую нумерацию или станет выпускать delta от старых баз, несовпадающие пары дадут
  только полный список или «проверка недоступна», но не ложный `good`. Расхождение CPS
  с наблюдаемым сроком delta (2 ч против ≈12 ч) не выяснялось у НУЦ.
- Проверка длинного пакета перед выдачей покрыта тестом. Для случая, когда срок истекает
  именно во время проверки цепочки TSA, работает тот же цикл, но отдельного теста нет:
  ответ TSA с синтетическим ключом не строит цепочку до корней НУЦ.
- Доступность корневого CRL зависит от WAF `crl.root.gov.kz`. После первого успешного
  скачивания список хранится до `nextUpdate` (около месяца).
- Реальные операции порталов и причина исходной ошибки контейнера пользователя
  по-прежнему не подтверждены.
